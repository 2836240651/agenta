## 1. 技术目标

验证并工程化这条可控链路：

```text
有头登录 CSP
  → storage_state 落盘
  → check（发品页门闸）
  → capture（人工发品，filtered 完整 body）
  → 固化 endpoints
  → APIRequestContext 回放创建/发布
  → storage_state 回写
```

**不是**立刻做 Commander 批量调度；**不是** UI 填表为主。

---

## 2. 为何抓包回放优先（相对纯 UI RPA）

| 维度 | 抓包 + API 回放 | 纯 UI 填表 |
|------|-----------------|------------|
| 抗 UI 改版 | 较强（仍怕接口改版） | 弱（selector 易碎） |
| 批量潜力 | 单次 HTTP 链，易限速扩展 | 每品整页重跑，慢 |
| 调试 | 请求/响应可落盘对比 | 依赖截图与人工眼看 |
| 与抖音参考差异 | 抖音以 UI 为主；本项目以回放为主、UI 仅登录/兜底 | — |

参考价值来自 SAU 的：**storage_state、有头人机登录、CLI 账号模型、门闸式 check、失败分级**；DOM 选择器流水线本身不照搬。

## 3. 技术前提与未知

### 3.0 2026-07-17 真实 tenant5 链路验证补充

- `tenant5` 的商品管理入口不是旧 `ait/cn_ams/item_choice/product_manage`，而是菜单返回的 `https://gsp.aliexpress.com/m_apps/choiceProductManage/list-manage?channelId=870088`，最终跳转到 `csp.aliexpress.com/m_apps/choiceProductManage/list-manage`。
- 商品列表主数据来自 `mtop.global.merchant.self.product.manager.render.list`，真实商品行在 `data.data.table.dataSource`；有效字段包括 `productId`、`catId`、`productCategory`、`itemDesc`、`subDataSource`。
- 编辑页 `product_publish?switchId=<productId>&from=SELF&channelId=<channelId>` 会返回 `mtop.item.product.self.publish.render`；该响应提供完整 `categoryPath`/表单骨架，但真实已上架商品的 `value.sku` 可能为空。
- 因此“已上架商品 → 训练样本”的当前可靠做法是 hybrid：`publish.render` 的 `value` 作为表单骨架，列表行 `subDataSource` 作为 SKU 证据补齐 `sku/logisticSku`，并在样本 `_sample_source.sku_source=listed_product_row` 标记来源。该标记表示后续 `draft.submit` 必须实测校验，不能把 hybrid 样本直接视为平台原生 draft body。
- 本次 tenant5 实测抓取 10 个已上架商品，得到 10 个 `sample_normalized`；`100005539|multi_sku` 与 `200075142|multi_sku` 达到 `ready_for_diff` 并生成 `profile_ready`。
- 使用 `100005539` 的 profile 生成 `draft.submit` payload 后，本地 dry-run 通过；live `draft.submit` 返回 `SUCCESS::调用成功`，提取到 `product_id=1005012758404676`。本次未调用 `publish.submit`。
- 鉴权判断不能仅用页面全文包含“登录/验证”作为失败条件；CSP 后台正常页面也包含相关文案。应优先识别工作台成功信号，如“商品管理”“商品列表”“草稿箱”“全托管”等，再判断登录/验证码失败。

### 3.1 已知 / 已决策

- Patchright 可做有头登录与 `storage_state`
- `switchId` / `channelId` 按账号配置，禁止全局写死
- MVP 回放通道固定为 **Playwright `APIRequestContext`**（同一 `BrowserContext`）
- `login` / `capture` 强制有头；`--headless` 仅 `publish`
- filtered 完整 body；jsonl 可截断

### 3.2 未知（设计 §14，M4 关闭）

- 媒体上传：OSS 直传 vs CSP 中转
- 「发布」= 提交审核 vs 直接上架
- CSRF / 业务 token 头名与刷新方式
- 是否存在额外签名参数（若有，须在同 Context 内取齐前置接口）

## 5. 登录与校验

### 5.1 登录

1. 解析账号 `login_url`（账号配置 > conf）
2. 有头启动 Chromium（可 channel=chromium）
3. `goto` 登录 URL；轮询直到判定登录完成或超时
4. 登录完成：`context.storage_state(path=cookies/csp_<account>.json)`
5. 未完成关闭浏览器：失败退出，不写「成功」态（或写无效并删除）

判定可参考：到达 `csp.aliexpress.com` 且非登录页；具体选择器在实现时按实页微调，**不得**弱化为「仅 URL 变化」若仍停在登录域。

### 5.2 check（写死）

1. `new_context(storage_state=...)`
2. 有头（默认可配置）打开 `publish_url`
3. URL 仍在 CSP 且与发品/后台相关
4. 无登录文案 → 通过；否则退出码 2

MVP **不做**「轻量 API whoami」双轨。

## 6. 抓包技术细节

### 6.1 监听

- `page.on("request")` / `response`（或 route）；只关注 XHR/fetch/文档类
- Host：`csp.aliexpress.com` 及相关网关（可配置）
- 剔除：静态资源、字体、大图、纯埋点（可配置弱化）

### 6.2 落盘语义（防逻辑断点）

| 文件 | body 策略 |
|------|-----------|
| `requests.jsonl` | 允许截断摘要（控盘） |
| `filtered.json` | **必须完整** request/response body |
| `critical/` | 过大时拆分；由 filtered 索引 |

违反「filtered 完整」则后续无法固化回放 → 视为 capture 失败。

### 6.3 停止条件

CLI 交互：操作者回车/Ctrl+C 结束；结束前 flush 文件；`meta.json` 写结束原因。

## 7. 回放技术路径（已选定）

### 7.1 MVP 路径：BrowserContext + APIRequestContext

```text
browser.launch(headless=publish旗标)
context = new_context(storage_state=...)
# 可选：先打开 publish_url 预热 cookie / 前端 token（若抓包证明需要）
api = context.request
按 endpoints 顺序：api.fetch / post ...
成功后：context.storage_state(path=cookie文件)
```

### 7.2 明确不采用（MVP）

- 默认 httpx/requests 拼 Cookie 却声称 RefreshCookie 写回标准 `storage_state`
- 无 endpoints 时「猜 URL」自动发布

### 7.3 降级策略

若同 Context 回放仍因签名失败：在 capture 中补录前置 token 接口，把「先 GET token 再 POST」写进 endpoints 步骤；仍不行则单独立项评估 UI 填表兜底（**超出本 MVP 成功判据**，记为路线阻塞）。

## 14. 2026-07-17 payload 净化、可见性与清理补充

### 14.1 payload 净化器

当前从“已上架商品 render/list hybrid 样本”生成 `draft.submit` body 时，不能直接复用旧商品的 SKU 身份与绑定字段。新增 `payload_sanitizer` 的职责是：

- 重建 `jsonBody.sku` 与 `jsonBody.logisticSku`，长度以目标商品 `sku_list` 为准。
- 删除旧商品身份、绑定、审核、锁定字段，例如 `skuId`、`scItemId`、`scInvId`、`productBarcode`、`skuTicketAudit`、`skuSaleLock`、`scItemInfo`、`scItemBind`、`cSpuBind`。
- 将新 SKU 写成安全临时身份：`id=custom_-1:-N`、`salePropKey=custom_-1--N`、`dpPricePropKey=dpcustom_-1--N`。
- 用目标商品覆盖 `sellerSkuCode`、`commodityCode`、`price/supplyPrice/selfGloEffectiveSupplyPrice`、`stock/selfSkuStock/skuTotalStock`。
- 在 payload 结果的 `diff.sanitized_fields` 与 `diff.removed_dangerous_fields` 中留下审计记录。

这一步的逻辑边界是“让草稿 payload 不携带旧商品身份”。它不能证明平台一定接受当前类目的全部业务字段，也不能替代草稿可见性校验。

### 14.2 channelId 是 live 回放上下文

本轮将 `scripts/run_draft_payload.py` 增加 `--channel-id`，并透传到 `fetch_mtop_step`。原因是 CSP 全托管发品链路依赖 mtop query 里的 `__channel-id__`；此前 live `draft.submit` 能返回 `SUCCESS` 与 `product_id=1005012758404676`，但列表页不可见，缺少 channel 上下文是高概率原因之一。

后续真实回放命令必须显式带上当前店铺的 `channelId`，例如：

```powershell
python scripts/run_draft_payload.py <draft_payload.json> --live --account tenant5 --channel-id 870088 --headless --out <draft_run.json>
```

### 14.3 草稿可见性校验

新增只读校验入口 `scripts/check_draft_visibility.py`：

- 打开 `https://csp.aliexpress.com/m_apps/choiceProductManage/list-manage?tab=<tab>&channelId=<channelId>`。
- 默认检查 `draft,pending_approval,violation_qc_failed,offline_product,online_product`。
- 只监听 `mtop.global.merchant.self.product.manager.render.list`，从 `data.data.table.dataSource` 中解析 `productId`。
- 输出 `visible` 或 `not_found`，并记录已检查标签页和响应数量。

本轮对旧回放结果 `product_id=1005012758404676` 的反查结果是：5 个标签页均 `not_found`。因此不能把此前的 `draft.submit SUCCESS` 认定为“后台可见草稿”。

### 14.4 清理策略

新增 `scripts/plan_cleanup_strategy.py`，它只根据可见性报告生成非破坏性人工清理建议：

- `draft`：建议人工进入草稿箱删除。
- `pending_approval`：建议人工撤回后再删除。
- `violation_qc_failed/offline_product/offline`：建议人工进入对应非在线标签删除。
- `online_product`：只给人工复核警告，禁止自动删除/撤回/下架。
- `not_found`：不做动作，提示未在检查标签页找到。

当前阶段不实现自动删除接口，也不扫描删除接口做回放。清理链路必须保持“先定位可见结果，再人工确认处理”。

### 14.5 当前 live 阻塞

本轮净化后的 payload dry-run 已通过，但 live 调用返回：

```text
FAIL_SYS_TOKEN_EXOIRED::令牌过期
```

这说明当前 `tenant5` cookie 里的 mtop token 已过期，未创建新草稿。下一次真实试跑需要先刷新登录态，再按“live draft.submit → 可见性校验 → 清理计划”的顺序执行。

### 14.6 2026-07-17 复跑结论：接口 SUCCESS 不等于草稿可见

后续复跑确认：`tenant5` 的 CSP 后台登录态可用，但 `_m_h5_tk` 过期会导致首次 mtop 请求返回 `FAIL_SYS_TOKEN_EXOIRED`。live runner 已改为在同一上下文中对该错误重试一次，并回写 storage_state。

更关键的发现是：`mtop.item.product.pop.publish.draft.submit` 可以返回 `ret=SUCCESS` 与一个长数字 ID，但该 ID 未必是 CSP 商品管理中可见、可编辑、可清理的草稿。

本轮证据：

- sanitized payload live 返回 `product_id=1005012758684812`，列表页 `draft/pending_approval/violation_qc_failed/offline_product/online_product` 均 `not_found`。
- 打开 `product_publish?switchId=1005012758684812&from=SELF&channelId=870088` 后，`mtop.item.product.self.publish.render` 返回 `THD_IC_ERR_F_IC_SERVICE_QUERY_002::Product not found`。
- 再次 live 返回 `product_id=1005012758936064`，列表页仍 `not_found`，编辑页 render 同样 `Product not found`。
- 历史 capture 里的 `draft.submit` 样本来自编辑态，外层 `itemId=1005012495417526`；当前 payload 作为新建草稿使用时外层 `itemId=""`。这两个场景不能等价。
- 历史 capture 还证明平台可能出现 `ret=SUCCESS` 但 `data.errorCode/globalError/models.globalMessage` 表示业务失败的响应，因此分类器必须优先检查 `data` 错误字段。

当前阶段判据调整：

1. `draft.submit` 返回 `SUCCESS` 只能叫“API 调用成功”，不能叫“草稿创建成功”。
2. 只有“列表页可见”或“编辑页 render 可打开”成立时，才能判定为可见草稿。
3. 继续扩展模板前，必须重新录制“新建商品保存草稿”的真实页面链路，找出新建态所需接口、外层字段、前置接口或后置确认动作。

### 14.7 2026-07-17 发布成功链路更正：switch.submit → publish.submit

重新审查历史录制后，找到了真实成功发布样本：`captures/live_20260715_125514`。该样本不是“空 itemId 直接 `draft.submit` 后可见”，而是两步链路：

```text
mtop.item.product.self.publish.switch.submit
  -> 返回 switchId=1005012739008238
mtop.item.product.pop.publish.submit
  -> 外层 itemId 使用上一步 switchId
  -> 返回 productId=1005012739008238 与 publish-success 页面模型
```

新的工程判断：

1. 新建发布链路的第一步应以 `self.publish.switch.submit` 创建当前页面上下文和 `switchId`，不能跳过该步骤。
2. 第二步 `pop.publish.submit` 必须使用本轮新鲜 `switchId`，并清除旧样品中的 `id/itemId/productId` 等身份字段。
3. `ret=SUCCESS` 仍不能单独作为成功标准；如果 `data.errorCode/globalError/errorCodes/models.globalMessage` 存在业务错误，必须判失败。
4. 当前新增能力只生成和净化两步 payload，不自动真实发布。真实发布必须增加显式确认参数，并在发布后用列表页或成功页做可见性/状态校验。

本轮落地：

- `uploader/csp_uploader/publish_chain.py`：抽取成功录制链路、分类响应、生成 `switch.submit` 与 `publish.submit` payload、用 `{{switchId}}` 占位避免旧 ID 外泄。
- `scripts/build_publish_chain_payload.py`：从成功录制目录生成可审计 JSON，默认不发网络请求。
- `tests/test_publish_chain.py`：覆盖成功链路抽取、伪成功业务错误、payload 净化、`switchId` 材料化和文件输出。

### 14.8 2026-07-17 受控发布试跑 runner

在生成两步 payload 后，新增受控 runner：

```powershell
python scripts/run_publish_chain.py <publish_chain_payload.json> `
  --out <publish_chain_run.json> `
  --account tenant5 `
  --channel-id 2078391
```

默认不调用真实接口，只写 `dry_run_passed` 或 payload 预检错误。真实发品必须同时传：

```powershell
--live --confirm-publish
```

live 语义：

1. 调 `mtop.item.product.self.publish.switch.submit`，从响应提取本轮 `switchId`。
2. 将 `publish.submit.itemId={{switchId}}` 材料化为本轮 `switchId`。
3. 调 `mtop.item.product.pop.publish.submit`，从响应提取 `productId`。
4. 发布后打开商品管理列表页，在 `pending_approval,online_product,violation_qc_failed,offline_product,draft` 中监听 `mtop.global.merchant.self.product.manager.render.list`，查找 `productId`。

结果判定：
